# Frontend architecture
- Car lists and pickers use sortCarsByNumber with BIL-prefix normalization so labels do not move numbered cars onto later pages; stored car numbers remain unchanged.
- Login effects are scoped to login-workspace; the existing form reports busy state for decoration without changing authentication or workspace visuals.
- Vacation approval/status changes use the derived approval capability; a database trigger guards status and reviewer fields independently of broader edit/read policies to preserve planning visibility and self-service.
- Calendar drag proposals use dnd-kit mouse/touch sensors and pure calendarDrag geometry; PlannerPage validates scope/availability and retains existing mutation, undo and series/form decisions, so gestures do not bypass permissions or introduce backend writes.
- Cross-department calendars load original tasks through each accessible department's existing authorized reader; retain source department IDs for mutations, resource selection and series matching instead of treating busy summaries as editable tasks.
- Dashboard presentation stays in existing widgets; preserve their hooks, filtering and action handlers when changing layout.
- Shared UI primitives retain their props and variants; visual defaults belong in semantic tokens and variant classes.
- Planner and dashboard operation summaries and deep links use the shared pure plannerOperations module; this keeps ISO-week scope, filters and overlap counts consistent.
- Planner cards consume PlannerWeekDataContext with a standalone fallback; this prevents per-card query subscriptions and repeated week conflict calculations without breaking other callers.
- Inbox state and drawer query keys are scoped to authenticated user IDs; authoritative catch-up reconciles mutations and missed realtime events without duplicate unread increments.
- Messaging worker ownership state uses endpoint-keyed IndexedDB tokens and a transactional latest pointer retaining account ownership; this prevents cross-endpoint token fallback and supports recovery.
- List pages share ListPageShell (department eyebrow, formatListCount meta, per-browser data-density) and the compact ModuleListTools row; row actions use shared RowActions with destructive items only in the menu.
- Module list toolbars are opt-in controlled UI; employee/car filters and vacation visibility-before-counting use shared pure helpers to retain the existing data hooks and action handlers.

- Edge authorization decisions live in src/security/backend/policies.ts with a byte-identical copy in supabase/staged/functions/_shared (test-enforced); unreviewed server changes are staged under supabase/staged/ so they are never auto-deployed.
- 3D-scanninger is a static app (public/3d/index.html, built outside this repo) shown inside PolyPlan on /3d-scanninger (ScansPage, same-origin iframe with ?embed=1) sharing PolyPlan's Supabase session, menu, login and light/dark; the frame reports the open tour via postMessage (origin and source checked). Access is read-only from user_roles via p360_* SQL, gated by useScanAccess.
- Embedded 3D documents retain their static /3d/index.html URL; only standalone documents normalize to /3d, because reloading the React /3d route inside the frame redirects away from the viewer.
- 3D-scanninger scenes are 360 photos or LiDAR scans (GLB, scene kind: model) shown by a built-in WebGL viewer; archived tours carry archAt and are purged client-side after 3 days by an editor's browser.
- Signed-out 3D visitors use the existing PolyPlan login page with an allowlisted /3d-scanninger (or legacy /3d) return destination and full-document navigation; the old /3d address moves into PolyPlan, while public insurer links (#l-) and recovery flows remain on the standalone page.
- Screen display reads through *_by_token functions when the address carries ?screen=<code> (src/lib/screenDisplayRpc.ts); codes live in screen_display_links (Admin → Skærme), are per department and revocable; anon access to the old department-ID functions is removed by staged 004 once screens are switched.
- index.html and the 3D build carry an inline clickjacking guard on polyplan.dk; only the exact read-only /screen-display route with a well-formed screen token may be framed externally. Other routes remain protected because the host cannot send frame-ancestors/X-Frame-Options headers.
- Screen links generated from Lovable editor/preview origins use the published app origin, because signage players cannot authenticate through Lovable's editor wall.
